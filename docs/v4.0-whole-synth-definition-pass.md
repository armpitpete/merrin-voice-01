# V4.0 — Whole Synth Definition Pass

## Purpose

This document defines the Merrin Grief Synth as a whole instrument family before hardware translation begins.

The current browser synth is the accepted proof-of-voice and control reference.

It is not the final destination.

The project goal is:

```text
Build Merrin Grief Synth — Constrained Grief as a real circuit-board synth.
```

The browser version exists to prove:

- the emotional voice
- the control language
- the signal path
- the performance surface
- the safety/recovery behaviours
- what should and should not be translated into hardware

This pass is still documentation/specification work only.

Do not add PCB work, circuit design, demo media, plugin work, VCV work, sequencer work, M A C controller work, DBHT-1 expansion work, or hardware expansion in this pass.

## What complete means at this stage

V4 is complete when the browser reference is clean enough to translate into hardware.

That means:

1. The voice identity is stable.
2. The main performance surface is clear.
3. Diagnostics are available but no longer dominate the instrument.
4. The final control set is accepted as the hardware candidate set.
5. The signal path language is final enough to translate into blocks.
6. MIDI/input behaviour is stable and recoverable.
7. Panic/reset/release behaviour is safe.
8. The app can be used by someone arriving cold.
9. The repo clearly says the browser synth is the reference, not the final product.
10. Hardware translation can then begin honestly.

Final demo media should still wait.

The proper next public demo should show either:

- the accepted browser reference, clearly labelled as reference, or
- the later hardware prototype, once it exists.

## Final reference shape

The browser reference should have two visible layers:

```text
Performance layer
Advanced/test layer
```

### Performance layer

The performance layer is the player-facing instrument reference.

It should contain:

- title / short identity sentence
- start audio / status / panic
- main playable controls
- voice-shaping controls
- emotion-shaped controls
- note input surface
- simple state feedback
- active-note visibility
- optional basic oscilloscope if it supports play rather than debugging

### Advanced/test layer

The advanced/test layer is for development, setup, and hardware translation evidence.

It may contain:

- MIDI diagnostics
- raw MIDI monitor
- effect test switches
- All effects off
- Normal voice reset
- Wither delay
- detailed voice state
- technical warnings

These must not feel like the public instrument surface.

They are allowed because they help prove and translate the circuit-board synth.

## Final signal path

The conceptual signal path remains:

```text
Scale
  ↓
Tone
  ↓
Envelope
  ↓
Room
  ↓
Memory
```

Module-language form:

```text
MV-02 Scale
  ↓
MV-01 Tone
  ↓
MV-03 Envelope
  ↓
MF-01 Room
  ↓
MF-02 Memory
```

Plain-language form:

```text
where the note is allowed to go
  ↓
what kind of voice speaks
  ↓
how it arrives and leaves
  ↓
what space holds it
  ↓
what trace remains
```

Hardware-translation meaning:

| Browser/reference block | Hardware question |
|---|---|
| Scale | Is constrained pitch handled by microcontroller, MIDI-to-CV logic, quantiser, or fixed note logic? |
| Tone | What oscillator/filter/waveshaping path gives the accepted voice? |
| Envelope | What attack/hold/release behaviour must be analogue, digital, or hybrid? |
| Room | Is space analogue, digital DSP, PT2399-style, FV-1-style, or omitted from first prototype? |
| Memory | What delay/echo/fading-trace behaviour is essential to the grief identity? |

This table is not circuit design yet. It is the handoff shape for the hardware translation lane.

## Final control set — hardware candidate draft

### Keep as main controls

| Control | Keep? | Hardware reason |
|---|---:|---|
| Tone | yes | Directly shapes allowed darkness/brightness. |
| Fade | yes | Defines grief-like arrival and disappearance. |
| Echo | yes | Gives memory/distance. |
| Amplitude | yes | Needed for safe output. |
| Shape | yes | Pure / Hollow / Pressed is core voice character. |
| Sub | yes | Adds body/weight without bass-feature drift. |
| Overtone | yes | Adds ache without shine. |
| Drift | yes | Adds small instability. |
| Scale | yes | Protects constrained pitch identity. |
| Glide | yes | Controls difficulty of movement. |
| Weight | yes | Gives heaviness. |
| Wither | yes | Gives fragile motion and weakening. |

### Move behind advanced/test in browser reference

| Control/tool | Reason |
|---|---|
| All effects off | Useful for checking translation blocks, not performance identity. |
| Normal voice | Useful reset, not main expression. |
| Effect test switches | Diagnostic only. |
| Raw MIDI monitor | Diagnostic only. |
| MIDI diagnostics | Useful but not main public surface. |
| Wither delay | Probably technical shaping rather than core player control. |

### Keep always reachable

| Control/tool | Reason |
|---|---|
| Start audio | Browser audio requirement. |
| Panic / all notes off | Safety and stuck-note recovery. |
| Status | Needed for browser/MIDI clarity. |

For hardware translation, `panic / all notes off` becomes a safety/reset/mute question rather than merely a browser button.

## Whole-synth behaviours to verify before hardware translation

### 1. Constrained grief remains audible

Changing controls should not turn the synth into a normal bright general-purpose synth.

### 2. Fast play does not break the identity

Fast note input may work, but it should not redefine the synth as a lead/pluck instrument.

### 3. Same-note retrigger remains stable

Repeated notes should retrigger musically and not overload.

### 4. MIDI/input remains stable

MIDI note-on/note-off should work without stuck notes, duplicate spam, or unsafe volume jumps.

### 5. Scale change remains safe

Changing scale must not leave illegal/stuck notes hanging.

### 6. Panic works

Panic must reliably silence active notes and recover normal play.

### 7. Diagnostics do not dominate

A cold visitor should see an instrument first, not a test rig.

### 8. The voice can return to accepted state

The player should be able to return from experiments to the accepted voice.

## What is missing before hardware translation

Hardware translation should wait until these are done:

1. Performance layer is accepted.
2. Advanced/test layer is separated cleanly.
3. Final control names are accepted.
4. README reflects browser-reference / hardware-destination status.
5. Roadmap says V4 reference acceptance is complete.
6. No known stuck-note or unsafe-output issue remains.
7. The app still feels like Constrained Grief after layout changes.
8. Hardware translation questions are listed without pretending circuits are already chosen.
